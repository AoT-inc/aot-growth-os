# 개요

## 1. 정체성

AoT Growth OS는 기업의 조직, 업무 절차, 정책, 지식, 성과, 전략을 하나의 코드 기반 운영체계로 통합한다.

| 축 | 의미 |
|---|---|
| 조직화 | 실제 기업 구조와 책임을 모델링 |
| 자율 실행 | 이벤트와 예약 루틴에 따른 업무 처리 |
| 지속적인 기억 | 세션에 의존하지 않는 기업 지식과 이력 |
| 평가와 개선 | 성과·비용·위험을 바탕으로 전략 갱신 |

최종 모습: 사람이 매번 AI에게 일을 시키는 환경이 아니라, 사람이 목표와 운영 규칙을 정의하면 시스템이 업무를 만들고, 담당 에이전트를 배정하고, 결과를 검사하고, 필요할 때만 사람에게 판단을 요청하는 환경.

## 2. 자체 개발 vs 재사용

AoT는 또 하나의 에이전트 프레임워크를 만들지 않는다.

| 영역 | 참고/재사용 후보 | 가져오는 것 | 가져오지 않는 것 |
|---|---|---|---|
| 조직·SOP | MetaGPT | 역할/산출물 전달/SOP 분해 아이디어 | 소프트웨어 개발 조직 역할 모델 전체 |
| 실행 조정 | LangGraph, Microsoft Agent Framework | 상태 기반 워크플로, 승인·재개 | 둘 다 도입 (동일 시나리오 시험 후 하나 선택, ADR-0009) |
| 코드 작업 | OpenHands | 격리된 코드 에이전트 실행 | 특정 제품 종속 (어댑터 뒤에 둠, ADR-0005) |
| 업무 기반 | Odoo, n8n, Temporal | CRM/회계/연동/장기 실행 | ERP 재구현 |

**자체 개발 계층** (이 저장소의 존재 이유):

- 조직과 책임의 정의
- 업무 및 이벤트의 공통 모델
- 기업 기억의 출처와 유효성
- 독립적인 결과 평가와 경제성 분석
- 전략의 버전 관리와 변경 승인
- 권한·정책·예산·공개 범위 통제
- 내부 웹과 외부 웹의 연결
- **개발 상품 레지스트리** (제품을 1급 객체로 관리하며 구동 후 검증·승인 절차로 등록, ADR-0010)

이 계층이 잘 설계되면 실행 프레임워크를 교체해도 업무 이력과 운영 규칙이 유지된다.

## 3. 아키텍처

초기에는 단일 저장소의 모듈형 모놀리스.

```
 사람(목표·감독·승인)        Claude Desktop(개발·운영 워크벤치, 상태를 소유하지 않음)
          │                              │
          ▼                              ▼
 ┌─────────────── AoT Growth OS ────────────────┐
 │ 조직·역할·전략   이벤트·루틴   업무 엔진·의존성 │
 │ 정책·권한·승인   기억·근거     평가·경제성·개선 │
 │ 상품 레지스트리                                │
 └───────┬──────────────────────┬────────────────┘
         ▼ (adapter)            ▼
 코드/전문 에이전트        MCP·API·CRM·이메일·웹 도구
         └──────────► 테스트·근거·결과 검증 ◄──────┘
 내부 웹: 업무·정책·보고서·승인      외부 웹: 콘텐츠·고객지원·공개정보
```

- **상태의 소유자는 데몬과 DB**이다. Desktop 세션이 종료되어도 예약 업무는 유지된다.
- 코드 에이전트는 어댑터 뒤에 둔다. 어떤 에이전트든 동일한 업무 명세를 받고 구조화된 결과와 실행 기록을 반환한다.
- 조직 구조는 `org_version`으로 관리하되 조직 관리팀은 제안만 하고, 권한 상승·보안 규칙 완화 같은 위험 변경은 일반 변경과 분리한다 (ADR-0006, ADR-0011).

## 4. 핵심 메커니즘

1. **루틴/이벤트 → 표준 업무**: 두 입구가 같은 업무 생성 엔진을 거친다. 중복 이벤트는 `idempotency_key`로 흡수 (ADR-0004).
2. **업무 명세**: 자유 프롬프트가 아니라 검증 가능한 구조체 (ADR-0003, `docs/schema/task-spec.md`).
3. **기억과 전략의 분리**: 기억은 출처·유효성을 가진 지식, 전략은 버전과 근거를 가진 의사결정 방향 (ADR-0008).
4. **평가 4축**: 결과 품질 / 업무 효과 / 경제성 / 안전성. 안전성은 거부권(veto) (ADR-0007).

## 5. 조직 구성: 적응형 ([ADR-0011](adr/0011-adaptive-organization.md))

부서를 처음부터 모두 만들지 않는다. 시작 조직은 **오너 + 조직 관리팀 + 범용 실행 역할 + 고정 코어**(검증기·평가기·정책·승인·비용 원장)뿐이다. 조직 관리팀이 사용자와 대화하며, `unassigned` 업무·반복 실패·비용 대비 효과·사람 개입 같은 **데이터 신호**를 근거로 `org_proposal`을 만든다. 승인 → 시험 기간(기본 2주) → 평가 → 확정 순으로 조직이 자란다. 구조는 유연하지만 권한 확대는 위험 변경이며, 조직 관리팀은 정책·검증기·평가기를 건드릴 수 없다.

아래 표는 확정 조직이 아니라 **목표 조직 후보**와 각 후보가 활성화될 때 필요한 통제다.

| 부서 | 초기 자동화 | 주요 통제 |
|---|---|---|
| 기획 | 시장 조사, 주간 전략 보고서 | 전략 변경 검토 |
| 마케팅 | 콘텐츠 조사·초안, 캠페인 평가 | 외부 게시 승인 |
| 영업 | 잠재 고객 조사, CRM 정리 | 외부 발송·고객 데이터 권한 |
| 생산·개발 | 코드 작업, 테스트, 릴리스 준비 | 격리 실행, 테스트, 코드 리뷰 |
| 고객 지원 | 문의 분류, 답변 초안 | 사실 검증, 민감 문의 이관 |
| 법무 | 계약 위험 항목 식별 | 법률 판단·확정은 사람 |
| 회계 | 지출 분류, 예산 감시 | 결제·송금 승인 분리 |
| 보안·네트워크 | 로그·구성 감시 | 권한 상승/운영 변경 통제 |

## 6. MVP: 하나의 완결된 업무 사이클, 두 단계로 구현

**주간 시장 조사 → 마케팅 실험 제안 → 승인 → 실행 → 성과 평가**

동시에 검증할 변수가 너무 많아지지 않도록 두 단계로 나눈다. Phase A에서 업무 엔진이 안정적임을 확인한 뒤, 그 실제 실패 사례와 업무 데이터를 근거로 Phase B에서 적응형 조직을 시험한다.

### Phase A — 실행 기반 검증 (고정된 최소 조직)
- 시드된 최소 조직과 범용 역할 (조직 관리팀 없이)
- SQLite 업무 상태 머신, 예약 루틴과 이벤트 처리
- 에이전트 어댑터와 구조화된 결과
- 결정론적 검증, 비용 기록
- 승인 대기, 데몬 재시작, 실패와 재시도, 실행 소유권(lease)과 부작용 멱등성
- 주간 사이클 1~7단계:
  1. 데몬이 주간 루틴으로 시장 조사 업무 생성
  2. 조사 에이전트가 출처·불확실성 포함 결과 제출
  3. 검증기가 출처 유효성·중복·주장-근거 일치 검사
  4. 기획 역할이 실험 후보 제안
  5. 평가기가 예상 효과·비용·위험·측정 방법 비교
  6. 사람이 승인하면 마케팅 업무/루틴 활성화
  7. 실제 결과를 비용과 함께 기록, 다음 주 전략에 반영

### Phase A 후속 — 상품 등록 (도그푸딩)
- 앱과 데몬이 내부 개발 환경에서 구동되면, 상품 등록 절차 [`candidate → verifying → pending_approval → registered`](products/README.md)를 첫 실제 업무로 수행한다.
- 제품 데이터는 공개 저장소에 두지 않고 내부 DB에만 등록한다 ([ADR-0010](adr/0010-product-registry.md), [공개 저장소 규칙](security/public-repository.md)).
- 주간 사이클의 `product_id`는 등록 완료 후 연결한다 (그 전에는 `NULL`).

### Phase B — 적응형 조직 검증
- `unassigned` 업무 및 반복 실패 분석
- `org_proposal` 생성과 기준 버전 충돌 검사
- 사람 승인과 제한된 시험 운영, 독립 평가와 `inconclusive` 처리
- 조직 버전 확정과 롤백(예약 루틴·진행 업무 처리 포함)
- 시험 결과를 다음 주 업무·전략 개선에 반영

**MVP 범위 통제**
- 업무 효과 측정은 **측정 가능한 신호 1개**로 고정. 나머지는 수동 입력/시뮬레이션.
- 검증은 결정론적 검사 → 컨텍스트 분리 LLM 검증 → 필요 시 사람.
- 영속화는 SQLite + 상태 머신 + 폴링 데몬. Temporal은 한계가 보이면 도입 (ADR-0009).
- 결제·계약 확정 같은 고위험 작업은 실제로 실행하지 않고, 정책 엔진의 거부 테스트와 승인 시뮬레이션으로 검증한다.

### MVP 통과 기준 (필수 테스트)

| 영역 | 필수 테스트 | Phase | 상세 |
|---|---|---|---|
| 데몬 복구 | 업무 실행 중 프로세스 종료 후 상태 복구 | A | [recovery](operations/recovery.md) |
| 중복 방지 | 동일 이벤트를 여러 번 전달해도 중복 업무와 외부 부작용 방지, 동시 워커 중 하나만 실행 | A | recovery |
| 승인 | 승인된 내용과 실행 인자가 다르면 실행 차단 | A | [task-spec](schema/task-spec.md) |
| 권한 | 역할 생성이나 라우팅 변경만으로 권한 확대 불가 | A(정책) / B | [trust-boundaries](security/trust-boundaries.md) |
| 정책 변경 | 실행 전에 정책이 강화되면 재검증 | A | task-spec |
| 평가 독립성 | 실행 에이전트의 보고서만으로 성과 확정 불가 | A | [evaluation](operations/evaluation.md) |
| 비용 | 모델 호출·도구 사용 비용을 업무 및 실행별로 집계 | A | |
| 외부 게시 | 승인 없는 콘텐츠와 내부 전용 데이터의 공개 차단 | A | trust-boundaries |
| 기억 | 반증된 정보와 만료된 정보를 현재 사실로 취급하지 않음, 외부 입력 지시문 무효 | A | [memory-item](schema/memory-item.md) |
| 조직 변경 | 오래된 기준 버전의 제안은 충돌 검출 | B | [state-machines](schema/state-machines.md) |
| 시험 평가 | 증거가 부족하면 `inconclusive` 처리, 즉시 중단 조건 | B | evaluation |
| 롤백 | 조직 버전 복구와 이미 발생한 부작용을 구분, 예약 루틴·진행 업무 처리 | B | state-machines |

## 7. 비목표

- 처음부터 모든 ERP 기능 재구현
- 마이크로서비스 선분리
- 무제한 셸/전체 네트워크 권한 부여
- 에이전트의 정책 자기 수정
- 전 부서 동시 자율화 / 부서의 사전 일괄 정의
- 조직 관리팀의 정책·검증기·평가기 수정
