# ADR-0004 이벤트·루틴은 멱등하게 업무로 변환된다

상태: proposed

## Context
이벤트는 중복 전달되고 루틴은 데몬 재시작 중 중복 발화할 수 있다. 같은 업무가 반복 생성되면 비용과 외부 부작용이 중복된다.

## Decision
- 업무 생성 입구는 하나(업무 생성 엔진)이며 루틴과 이벤트 모두 거친다.
- `event.idempotency_key`는 `(source, external_id)` 또는 내용 해시로 만들고 unique 제약을 둔다.
- 루틴 발화는 `routine_firing(routine_id, scheduled_for)` unique 제약으로 한 번만 기록한다. 놓친 발화는 정책(`catch_up: skip|run_once`)에 따른다.
- `task.dedupe_key`로 동일 트리거·동일 입력의 활성 업무 중복 생성을 막는다.
- 실패 시 상태를 보존하고 `retry_wait`로 간다. 재시도는 새 `task_run`을 만들며 업무는 같다.
- 외부 부작용이 있는 도구 호출은 호출별 idempotency token을 사용한다.

## Consequences
- 스키마 첫 버전에 키/제약을 포함해야 한다(후행 추가가 어려움).

## Amendment (2026-10-14): 실행 소유권과 부작용 멱등성
생성 멱등성만으로는 중복 부작용을 막지 못한다. 세 수준을 구분한다: 업무 생성 / 실행 소유권(lease) / 외부 부작용.
- `task_run`에 `lease_owner`, `lease_expires_at`, `heartbeat_at`, `checkpoint`를 둔다. 업무당 활성 run은 하나.
- 외부 부작용은 `external_effect`(`effect_key` UNIQUE)로 기록한다. 외부 시스템이 멱등 키를 지원하지 않고 결과가 `unknown`이면 자동 재시도하지 않고 외부 상태를 조회하거나 `needs_review`로 보낸다.
- 상세와 복구 시나리오는 [operations/recovery.md](../operations/recovery.md).

## Amendment (2026-10-24): 루틴 일정 형식과 발화 규칙
`routine.schedule`("cron + tz" 한 열)의 형식과 발화 시각 규칙을 정한다. 스키마는 바뀌지 않는다.
- **형식:** `<분> <시> <일> <월> <요일> <IANA tz>` — 공백으로 나뉜 6개 토큰, 예 `0 9 * * 1 Asia/Seoul`. 시간대는 필수(없으면 거부, 조용히 UTC 로 가정하지 않는다). 각 필드는 `*`, 숫자, 목록, 범위, 간격(`*/15`, `10-40/10`)만 지원한다. 월(`JAN`-`DEC`)과 요일(`SUN`-`SAT`, 0·7 = 일요일) 이름은 대소문자 무시로 받는다. `?`, `L`, `W`, `#`, `@daily` 별칭, 초·연도 필드, UTC 오프셋(`+09:00`)은 구현하지 않고 사유와 함께 거부한다. 일과 요일을 둘 다 제한하면(둘 다 `*` 로 시작하지 않으면) 표준 cron 처럼 둘 중 하나만 맞아도 발화한다.
- **시간대 경계:** 슬롯은 "벽시계 시각 하나당 순간 하나"다. 봄 전환으로 존재하지 않는 시각(뉴욕 3월 02:30)은 건너뛴 길이만큼 뒤로 밀려 발화하고(03:30 EDT), 밀려서 다른 슬롯과 같은 순간이 되면 하나로 합친다. 가을 전환으로 두 번 나타나는 시각(뉴욕 11월 01:30)은 앞선 쪽 한 번만 발화한다. 따라서 겹친 시간대의 두 번째 정시(예: `0 * * * *` 의 두 번째 01:00)는 슬롯이 아니다.
- **`catch_up`:** `skip` = 놓친 슬롯은 버리고 다음 슬롯부터 정상 진행한다. `run_once` = 놓친 슬롯 중 가장 최근 1개만 발화하고 나머지는 버린다. 어느 쪽이든 허용 지연(기본 10분, 설정 가능) 안에 도래한 슬롯은 "놓친" 것이 아니라 "늦은" 것이라 발화한다(긴 업무 실행 중 도래한 슬롯을 잃지 않기 위해). 버린 슬롯은 `routine_firing` 에 기록하지 않는다 — 기준점은 마지막 발화의 `scheduled_for` 이고, 한 번도 발화하지 않은 루틴은 켠 시각(주입값) 또는 프로세스가 처음 본 시각이다.
- **템플릿:** `task_template` 은 `RoutineTemplateSource` 포트가 업무 명세 1개 이상으로 해석한다. 업무끼리는 템플릿 안 이름(`name`, `dependsOn`)으로 의존하고, 발화가 이름을 생성된 업무 id 로 바꿔 `task_dependency` 에 넣는다. 한 발화의 업무 전부와 `routine_firing` 은 한 트랜잭션이라 하나라도 거부되면 발화 기록도 남지 않는다. 형제 업무는 같은 trigger·입력이어도 `dedupe_key` 에 이름이 들어가 하나로 합쳐지지 않는다.
