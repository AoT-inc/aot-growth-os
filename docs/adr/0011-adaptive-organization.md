# ADR-0011 적응형 조직 구성

상태: proposed

## Context
부서 8개를 처음부터 정의하면 실제 업무 없이 구조를 추측하게 된다. 조직은 업무와 평가 결과를 보며 점진적으로 만들어지는 편이 낫다. 단, 조직 재편이 권한 상승 경로가 되면 안 된다.

## Decision

### 1. 시작 조직은 최소로 한다
- **사람**: 오너(목표·제약·승인 주체).
- **조직 관리팀**(`org-management`): 사용자와 대화하며 조직 변경안을 만드는 역할.
- **범용 실행 역할** 1~2개(`generalist`).
- **고정 코어**: 검증기, 평가기, 정책·승인 엔진, 비용 원장. 조직 관리팀이 수정할 수 없다.
- 기존 부서 목록(기획·마케팅·영업 등)은 "목표 조직 후보"일 뿐 초기 구성이 아니다.

### 2. 구조는 유연하게, 권한은 고정한다
| 구분 | 조직 관리팀의 권한 |
|---|---|
| 부서·역할 구성, 업무 라우팅, 루틴, 워크플로 템플릿 | 제안 가능, 일반 승인 |
| 도구 권한 확대, 예산 상향, 외부 게시 범위 확대, 운영 환경 접근, 승인 요건 삭제 | 제안만 가능, **위험 변경**(ADR-0006의 별도 승인) |
| 정책, 검증기, 평가기, 승인 엔진 | 접근·제안 불가 (정책 변경 절차로만) |

역할의 `allowed_tools` 등 권한 필드는 역할이 만들어져도 정책이 최종 결정한다. 역할 생성만으로 권한이 생기지 않는다.

### 3. 조직 변경은 제안 객체를 거친다
- `org_proposal`: 변경 내용(diff), 이유, 근거(`evaluation`/`task` 통계/`memory_item` 참조), 예상 효과와 위험, 변경 등급(`normal|risky`).
- 흐름: `proposed → approved → trial → active`, 거절 시 `rejected`, 실패 시 `rolled_back`.
- 승인 후 곧바로 `active`가 되지 않고 **시험 기간(`trial`)** 을 거친다. 기본 최소 2주(주간 사이클 2회). 시험 기간 동안 영향 범위는 제안에 명시한 업무 유형으로 제한한다.
- 확정마다 `org_version`을 만들고 이전 버전으로 롤백할 수 있다.

### 4. 조직 관리팀은 자기 변경을 평가하지 않는다
시험 결과의 판정은 평가 모듈이 한다(ADR-0007). 조직 관리팀은 결과를 보고 다음 제안을 만들 수 있을 뿐이다.

### 5. 재편 신호는 데이터로 정의한다
조직 관리팀의 변경안은 대화 인상이 아니라 아래 신호를 근거로 한다. 대화는 신호를 보여 주고 사용자의 의도·제약을 받는 수단이다.

| 신호 | 의미 |
|---|---|
| `unassigned` 업무 | 맞는 역할이 없음 → 역할/부서 신설 후보 |
| 역할별 반복 `needs_review`·`failed` | 역할 범위 재조정, 분리, 폐지 후보 |
| 업무 유형별 비용 대비 효과 저조 | 루틴/워크플로 축소·폐지 후보 |
| 사람 개입 시간의 반복 구간 | 자동화 대상 또는 책임 재배정 후보 |
| 한 역할의 업무량 편중 | 분할 후보 |

### 6. 이력은 버전으로 보존한다
역할·조직 단위는 버전을 가진다. 업무는 생성 시점의 `org_version_id`와 `role_version`을 기록하여, 조직이 바뀌어도 "그때 그 역할이 한 일"로 추적된다. 역할 폐지(`retired`)는 삭제가 아니다.

### 7. 역할 수명주기
`proposed → trial → active → retired`. 업무 배정은 `trial`·`active` 역할에만 가능하며, `trial` 역할은 제안에 명시된 업무 유형만 받는다.

## Consequences
- 실제 업무로 검증되지 않은 부서를 만들지 않는다. 구조 정의 비용이 줄고 근거가 남는다.
- MVP 검증 범위가 늘어난다. 변수를 줄이기 위해 Phase A(고정 최소 조직으로 업무 엔진 검증) 이후 Phase B에서 조직 변경 제안 → 승인 → 시험 → 평가 흐름을 검증한다(아래 Amendment 5).
- 조직 관리팀 오작동 위험이 있으므로 변경 제안은 항상 diff와 근거를 포함해야 하며, 승인 없는 적용 경로는 없다.
- 업무 라우팅에 `unassigned` 상태가 필요하다([state-machines](../schema/state-machines.md)).

## Amendment (2026-10-14): 증거 기반 시험 종료, 충돌 검사, 롤백

1. **시험은 시간이 아니라 증거로 종료한다.** `trial` 진입 전에 성공 기준, 실패 기준, 즉시 중단 조건, 허용 비용, 최소 관측 횟수, 데이터 품질 조건, 비교 기준선, 평가 기간을 `evaluation_plan`에 확정한다. 판정은 `pass` / `fail` / `inconclusive`이며 관측 수가 부족하면 `inconclusive`다. 안전성 위반·예산 초과·심각한 품질 저하는 기간과 무관하게 즉시 중단한다. 기본 14일은 최소 기간이며 `active` 승격에는 최소 관측과 성공 조건이 필요하다. 연장은 자동 허용하지 않는다.
2. **제안 충돌 검사.** `org_proposal`에 `base_org_version_id`, `proposal_hash`, `scope`, `risk_assessment`, `evaluation_plan`, `rollback_plan`, `expires_at`을 둔다. 승인 시점에 기준 버전이 현재 버전과 다르면 충돌로 처리하고 최신 기준으로 재제안한다. 조직 변경은 JSON 덮어쓰기가 아니라 승인된 diff를 적용해 새 `org_version`을 만드는 작업이다.
3. **상태 추가.** `inconclusive`, `retired`, `expired`, `superseded`. 시험 실패(`trial → rolled_back`)와 확정 후 롤백(`active → rolled_back`)을 구분한다. `approved`는 변경안 승인이지 무조건적인 실행 허가가 아니다.
4. **롤백 범위.** 조직 버전 복구뿐 아니라 새 역할의 예약 루틴, 진행 중·대기 업무 처리를 `rollback_plan`에 정의한다. 이미 발생한 외부 부작용은 자동 복구되지 않으며 보상 업무 또는 사람의 처리가 필요하다. 역할 폐지는 업무 기록과 책임 이력을 보존한다.
5. **개발 단계.** 조직 관리팀의 제안·승인·시험·평가는 Phase B에서 구현한다 ([overview §6](../00-overview.md)). Phase A는 고정된 최소 조직으로 실행 기반을 검증한다.
상세 상태 전이는 [state-machines](../schema/state-machines.md), 평가 규칙은 [operations/evaluation.md](../operations/evaluation.md).
