# ADR-0018 오너의 MCP 서버는 호스트 커넥터 프로세스가 오너 선언 도구만 게이트웨이로 내준다

상태: proposed (2026-11-09. 설계와 작업 순서는 [plans/mcp-connector](../plans/mcp-connector.md)). 개정 1 (2026-11-10): 로그인 위임 토큰(`oauth_delegated`) — 아래 "개정 1" 절이 Decision 5 를 이 인증 종류에 한해 바꾼다.

## Context
오너는 자기 사이트(웹사이트, 프로젝트 도구, 강좌 플랫폼, 인증 사이트)마다 MCP 서버를 만들고 있고, 성장 운영 에이전트가 그 도구를 쓰기를 원한다. 지금 에이전트는 run 마다 선언된 호스트 도구만 부를 수 있다: 명세 `allowed_tools`(`apps/daemon/src/agent-executor.ts`)가 게이트웨이(`packages/agent-runtime/src/gateway.ts`)에 열 도구를 고르고, 호출마다 정책(`packages/policy/src/tool-call.ts`)이 판정하며, 부작용은 부작용 원장(`performEffect`)을 지난다. Claude Code 경로는 게이트웨이 하나만 MCP 서버로 보이고(`--strict-mcp-config`) 다른 MCP 서버가 보이면 격리 위반으로 끝낸다(`claude-code/stream.ts`). 외부 MCP 서버를 에이전트에 직접 붙이면 정책 재판정·비밀 주입·호출 기록을 모두 건너뛰기 때문이다([trust-boundaries §3](../security/trust-boundaries.md)).

MCP 서버는 도구 목록·입력 스키마·설명·`readOnlyHint` 같은 주석을 스스로 알린다. 이 값은 서버가 바꿀 수 있고(목록 변경 알림, 배포), 서버 코드나 서버가 다루는 콘텐츠가 오염되면 거짓일 수 있다. 도구 결과에는 사이트 방문자·학생·고객이 쓴 글이 섞인다. 서버는 거꾸로 클라이언트에 요청(LLM 호출 `sampling`, 사용자 입력 `elicitation`, `roots`)을 보낼 수도 있다. [ADR-0012](0012-extension-unit-contract.md) §2는 커넥터를 게이트웨이 계약 뒤의 별도 프로세스로 두기로 했으나 아직 하나도 없다.

## Decision
1. **에이전트는 외부 MCP 서버를 보지 못한다.** 호스트(데몬)가 사이트마다 **커넥터 프로세스** 하나를 띄우고, 커넥터만 MCP 클라이언트로 서버에 접속한다. 커넥터는 DB·`policies/`·`instance/`에 접근하지 않고(ADR-0012 §2) 데몬과는 stdin/stdout 줄 단위 JSON으로만 통신한다. 에이전트가 부르는 것은 늘 게이트웨이 도구이며, Claude Code 경로의 "게이트웨이 외 MCP 서버 = 격리 위반" 규칙은 그대로다.
2. **도구는 오너 선언(manifest)으로만 존재한다. 기본은 거부다.** 데몬 설정 `mcp_sites[]`가 사이트별로 내줄 도구를 하나씩 선언한다: 에이전트용 이름, 오너가 쓴 설명, `scope`, `impact`, `side_effect`, 부작용이면 `approval: draft|scope`, 정책 대상 `target`, 고정한 입력 스키마 해시. 선언하지 않은 서버 도구는 에이전트 도구 목록에도, 커넥터가 부를 수 있는 목록에도 없다. 선언된 도구도 명세 `allowed_tools`와 호출별 정책 판정을 지나야 열린다(기존 규칙).
3. **분류는 오너 선언만 따른다.** 서버의 `readOnlyHint`·`destructiveHint`·`idempotentHint`·설명은 분류·정책·승인 판단에 쓰지 않는다. 에이전트에게 보이는 설명도 오너가 쓴 문장이며 서버 설명은 전달하지 않는다(설명을 통한 지시 주입 차단). 단, 오너가 읽기로 선언한 도구를 서버가 읽기 전용이 아니라고(`readOnlyHint:false` 또는 `destructiveHint:true`) 알리면 그 도구를 열지 않는다(오너가 확인 표시 `ack_server_hint_conflict`를 달 때까지). 더 위험한 쪽의 불일치만 막고, 더 안전한 쪽 주장은 무시한다.
4. **쓰기는 부작용 원장을 지난다.** `side_effect: true` 도구는 영향 `external_effect`이고 실행기는 원장에 묶인다(`bindToEffectLedger`). `approval: draft`(바깥으로 나가는 내용: 게시, 학생·고객에게 가는 글, 인증서 발급)는 [ADR-0015](0015-draft-before-approval.md)대로 초안 run이 정확한 인자를 초안으로 남기고, 사람(또는 [ADR-0016](0016-decision-delegation.md) 위임)이 그 초안을 승인한 뒤 호스트 전송 run이 **승인된 인자 바이트 그대로** 커넥터를 통해 `tools/call` 한다. `approval`을 빠뜨린 쓰기 선언은 거부한다. 응답을 잃거나 시간이 지나면 `unknown`이고 자동 재전송하지 않는다(MCP에는 표준 멱등 키가 없다). 오너가 멱등 키를 받을 인자를 선언한 도구만 같은 키로 재전송할 수 있다.
5. **비밀값은 커넥터에만 있다.** 데몬 설정에는 환경 변수 *이름*만 적는다. 데몬이 시작할 때 값을 읽어 커넥터 프로세스의 환경으로만 넘기고(그 밖의 환경은 넘기지 않는다), DB·로그·호출 기록·초안·에이전트 입력 어디에도 싣지 않는다. 커넥터는 서버 응답에 비밀값이 그대로 되돌아오면 가린 뒤에 데몬에 넘긴다.
6. **도구 결과는 외부 입력이다.** 모든 MCP 결과는 `resultOrigin: 'external_untrusted'`라 그 run의 뒤 호출이 외부 입력 영향으로 표시되고, 부작용 호출은 승인이 필요해진다(게이트웨이 하한 + 정책 상향). 초안은 만들 수 있으나 표시가 남고 위임 승인 대상이 아니다(ADR-0016). 쓰기 도구의 서버 응답은 에이전트에 돌려주지 않는다(상태만).
7. **스키마 고정과 변화 감지.** 커넥터는 시작할 때, 목록 변경 알림을 받을 때, 주기적으로, 그리고 쓰기 전송 직전마다 `tools/list`를 다시 읽는다. 선언된 도구의 입력 스키마 해시가 고정값과 다르거나 도구가 사라지면 **그 도구만** 닫고(호출은 `tool_error`, 전송은 보내기 전 `failed`) 운영 로그에 남긴다. 서버가 새 도구를 더한 것은 무시하고 기록만 한다. 다시 여는 것은 오너가 새 해시를 확인해 선언을 고치는 일뿐이며 자동 승인은 없다.
8. **시간·속도 제한과 서버 요청 거부.** 읽기는 도구 타임아웃(기본 20초) 뒤 게이트웨이가 `tool_timeout`으로 답하고 서버에 취소를 보낸다. 사이트마다 분당 호출 상한(기본 30)을 호스트가 세고, 넘친 읽기는 즉시 거부, 전송은 상한 안에서 기다린다. 커넥터는 클라이언트 기능을 하나도 알리지 않고 서버가 보내는 요청(`sampling`·`elicitation`·`roots` 등)은 모두 거절한다.

> MCP 서버가 없는 서비스의 HTTP API 는 같은 커넥터 프로세스의 전송 종류 `api` 로 붙인다 — [ADR-0020](0020-api-connector.md). Decision 1~8 을 그대로 따른다.

## Consequences
- 오너는 새 사이트를 붙일 때 도구를 하나씩 읽고 분류해야 한다(설명·분류·대상·스키마 해시). 고정 해시를 출력하는 확인 명령을 둔다. 운영 절차는 [operations/mcp-sites](../operations/mcp-sites.md).
- 서버가 스키마를 바꾸면 그 도구는 오너가 다시 고정할 때까지 멈춘다. 자주 배포하는 사이트는 그만큼 오너 결정이 늘어난다(알려진 비용).
- 쓰기 결과가 `unknown`이면 사람이 `resolve-effect`로 확정한다. 멱등 키 인자가 없는 사이트에서는 이 일이 남는다.
- MCP 표준이 바뀌면(프로토콜 버전) 커넥터만 고친다. 외부 라이브러리 의존을 더하지 않고 필요한 부분(초기화, `tools/list`, `tools/call`, 취소, 목록 변경 알림, Streamable HTTP·stdio)만 직접 구현한다([ADR-0009](0009-build-vs-reuse.md): 코어는 런타임 의존이 0개다).
- 커넥터는 신뢰된 호스트 코드지만 신뢰하지 않는 응답을 해석한다. 별도 프로세스이므로 해석 오류가 데몬의 DB·정책·승인 채널로 번지지 않는다. 별도 OS 사용자·컨테이너 격리는 하지 않는다(오너 결정 대상, 설계 §9).
- 이 ADR은 [ADR-0012](0012-extension-unit-contract.md) §2의 첫 구현이다. 팩이 커넥터를 *제공*하는 길은 아직 없다: 커넥터 선언은 데몬 설정(오너)만 쓴다.

## 개정 1 (2026-11-10) — 로그인 위임 토큰 `oauth_delegated`

### Context
오너 사이트(aot-project, aot-course 등)는 중앙 인증(aot-auth)의 OAuth2 접근 토큰(JWT, 수명 1시간, `aud` = 사이트 `resource`)으로 MCP 를 받는다. 갱신 토큰은 30일이고 **쓸 때마다 교체되며, 교체된 옛 토큰이 다시 들어오면 허브가 그 연결 전체를 끊는다**(aot-auth DESIGN §3-3). 기존 `bearer`/`header` 는 데몬이 시작할 때 환경 변수를 한 번 읽어 커넥터에 넘기므로 1시간마다 바뀌는 토큰을 실을 수 없다. 오너가 한 번 로그인하면 에이전트가 오너 권한(범위로 줄인)으로 사이트 도구를 쓰는 것이 1단계 목표다(에이전트 신원은 2단계).

### Decision (Decision 5 의 개정: `oauth_delegated` 에만 적용. `bearer`/`header`/`none` 은 그대로)
1. **갱신 토큰은 데몬 호스트 쪽에만 있다.** 로그인 명령(`mcp-login <site>`)이 `instance/mcp-auth/<site>.json`(디렉터리 0700, 파일 0600, 원자적 쓰기)에 갱신 토큰·동적 등록 `client_id`·접근 토큰과 만료 시각을 쓴다. 이 파일을 읽고 쓰는 것은 데몬 프로세스(토큰 원천)와 로그인 명령뿐이다. **커넥터는 `instance/` 에 접근하지 않는다**([ADR-0012](0012-extension-unit-contract.md) §2 유지). Decision 5 의 "비밀값은 커넥터에만 있다" 중 *갱신 토큰*은 이 개정으로 예외다: 갱신 토큰은 커넥터 프로세스 환경·설정 줄·DB·로그·호출 기록·초안·에이전트 입력 어디에도 가지 않는다.
2. **커넥터에는 접근 토큰만 간다.** 데몬이 커넥터 stdin 으로 `{"type":"token","access_token":…|null}` 줄을 보낸다(설정 줄이 아니라 별도 메시지라 환경에도 안 남는다). 커넥터는 메모리에만 두고 요청마다 `Authorization: Bearer` 로 싣고, 서버 응답에 되돌아오면 Decision 5 대로 가린다. 접근 토큰 자체는 데몬 DB·로그에 싣지 않는다(데몬 프로세스 메모리와 위 파일에만).
3. **갱신은 데몬 한 곳, 한 번에 하나.** 사이트마다 토큰 원천 하나가 만료 5분 전(수명이 짧으면 절반 지점)에 갱신하고 동시에 하나만 돈다. 새 갱신 토큰은 **디스크에 쓴 뒤에** 쓴다. 로그인 명령은 갱신하지 않는다. 확인 명령(`mcp-pin`)은 파일의 접근 토큰이 유효할 때 읽기만 하고 갱신하지 않는다(갱신 주체가 둘이면 재사용 감지로 연결이 끊긴다).
4. **갱신 실패의 처리.** 허브가 거절(`invalid_grant` 등 4xx)하면 확정 실패: 그 사이트 커넥터의 토큰을 거두고(`null`), 갱신 토큰 파일 내용을 지우고, 도구 상태 `closed:unauthorized` 로 닫는다. 서버 오류(5xx/429)와 연결 거부·DNS 실패는 요청이 확정되지 않았으므로 지수 대기로 재시도한다(접근 토큰이 만료되면 같은 닫힘). **응답을 잃은 모호한 실패(시간 초과, 보낸 뒤 끊김)는 재시도하지 않는다**: 허브가 이미 교체했다면 옛 토큰 재사용으로 연결 전체가 끊기기 때문이다. 이 경우도 닫고 오너가 다시 로그인한다. 닫힘은 그 사이트의 도구에만 영향이 있다. 확정 실패·모호한 실패마다 운영 이벤트(`auth_failed`)와 오너 알림 파일(`instance/mcp-auth/<site>.notice.json`: 시각, 이유, 할 일 `mcp-login <site>`)을 남기고, 다시 로그인하거나 갱신이 성공하면 지운다. 사이트가 401 을 돌려주면(폐지 목록 등) 토큰 원천이 바로 한 번 갱신을 시도한다.
5. **선언.** 인증 종류 `oauth_delegated`: `{ "kind": "oauth_delegated", "hub": "https://<허브>", "resource": "<사이트 /mcp 주소>", "scopes": ["…"] }`. 전송은 `http` 만이고 `resource` 의 출처는 전송 URL 의 출처와 같아야 한다(다른 호스트로 토큰이 나가지 않게). `hub` 는 https(루프백만 http)이고 경로가 없다. 요청 범위는 오너가 적는 최소 목록이며 허브가 줄여 줄 수 있다. 로그인 명령은 허브 메타데이터(`/.well-known/oauth-authorization-server`)의 엔드포인트가 허브와 같은 출처가 아니면 거부한다.
6. **로그인(`mcp-login`)** 은 인가 코드 + PKCE(S256) + 동적 클라이언트 등록(RFC 7591, 공개 클라이언트 `token_endpoint_auth_method: none`)이고, 되돌림 주소는 `127.0.0.1` 의 임의 포트 루프백이다(허브 허용 목록 `http://127.0.0.1` 이 이미 있다). 인가 요청에 `resource` 를 싣는다(RFC 8707).

### Consequences
- 위임 토큰은 **오너 권한 그대로**다(관리자면 사이트의 `policy.can` 이 모두 통과). 범위와 오너 선언 도구 목록이 유일한 울타리이므로 처음에는 읽기 범위와 초안 쓰기 범위만 요청하고, 선언하지 않은 도구는 어디에도 열리지 않는다(Decision 2·6 불변).
- 서명 키가 데몬 호스트의 `instance/` 에 닿는 사람이면 갱신 토큰도 읽는다. 이는 이미 `instance/` 에 있는 TOTP 비밀·정책과 같은 신뢰 수준이다.
- 오너가 비밀번호+TOTP 로 로그인해야 하는 일(30일마다, 또는 갱신이 모호하게 실패했을 때)이 생긴다. 알림 파일과 `mcp-login --status` 가 그 시점을 알린다.
- 에이전트 신원(2단계)이 생기면 이 절의 "오너 권한 그대로" 전제를 다시 본다.
