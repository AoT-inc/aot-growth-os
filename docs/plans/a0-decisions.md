# A0 착수 전 결정 초안

상태: 일부 결정 (2026-10-19: D1·D4·D6·D7 결정, D2·D3·D5 대기)

[Phase A 계획](phase-a.md)의 A0(저장소 부트스트랩)를 시작하기 전에 **사람이 정해야 하는 항목**을 선택지와 권장안으로 정리한다. 권장안은 제안일 뿐이며, 결정되면 [open-questions](../open-questions.md)의 해당 행을 "해소"로 바꾸고 아래 "기록 위치"에 반영한다.

공개 저장소이므로 실제 제품명·지표 이름·사람 이름은 이 문서에 쓰지 않는다. 그런 값은 `instance/`에 기록하고, 여기에는 결정의 **형식**만 남긴다 ([공개 저장소 규칙](../security/public-repository.md)).

## 0. 이 초안이 필요한 이유 (계획 검토 요약)

| 관점 | 판단 | 근거 |
|---|---|---|
| 적절성 | 대체로 충족. 다만 사용자 가치가 늦게 나온다 | 신뢰성·통제(복구, 승인, 독립 평가)는 비전과 맞는다. 하지만 Phase A는 인프라 검증이 대부분이고, 사용자가 체감하는 첫 결과(주간 조사, 상품 등록)는 A6 이후다. 측정 신호(Q5)가 정해지지 않으면 7단계 평가가 성립하지 않는다 |
| 확장성 | 코어 모델은 업종 중립적, 확장 방법은 미정 | `task`·`event`·`policy`·`evaluation`·`memory_item`은 업종과 무관하다. 그러나 주간 사이클이 코어에 붙박혀 있고, `product`가 소프트웨어 저장소 중심이며, 업종별로 업무·검증기·도구를 더하는 **확장 단위**가 정의되어 있지 않다 |
| 배포 유효성 | 아직 불가 | 라이선스가 없고, 인스턴스 분리(`instance/`, `*.example`)는 좋지만 설치·격리 환경(Q26)·승인 채널(Q25)이 특정 개인 환경을 가정할 위험이 있다 |

결론: A0·A1은 되돌리기 쉬운 작업이라 진행해도 된다. 다만 아래 7개 항목은 A0에서 만들 골격(언어, 패키지 배치, 시드 데이터, 라이선스 파일)을 바꾸므로 먼저 정한다.

## D1. 런타임과 DB (Q2)

**결정: A (TypeScript + SQLite, Node LTS, Postgres 이식 가능 DDL 유지) (2026-10-19).** 기록: [ADR-0001](../adr/0001-modular-monolith.md) accepted.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. TypeScript + SQLite** | ADR-0001 가정과 일치. 타입으로 `task_spec` 계약을 강제하기 쉽다. 단일 파일 DB라 설치·백업이 쉽다 | 오케스트레이션 후보(Q3) 생태계는 Python 쪽이 더 두껍다 |
| B. Python + SQLite | LangGraph·Agent Framework·OpenHands와 같은 언어 | 모듈 경계·타입 강제가 약하다. 배포 시 가상 환경 관리 부담 |
| C. TypeScript + Postgres부터 | 동시성·운영 이식 문제가 처음부터 없다 | 다른 사람이 받아 쓰려면 DB 서버가 필요하다. Phase A 범위에 비해 무겁다 |

**권장: A.** 에이전트 제품은 어댑터 뒤의 하위 프로세스이므로 언어가 달라도 된다(ADR-0005). SQLite 접근 계층·마이그레이션 도구는 Q24에서 고른다.

사람이 확인할 것: 기존 제품들의 주력 스택이 TypeScript와 크게 다르지 않은가(유지보수 인력 관점).

## D2. 측정 신호 1개 (Q5)

선택 기준(모두 만족해야 한다):
1. 주간 단위로 [평가 규칙](../operations/evaluation.md)의 최소 관측 수를 채울 만큼 값이 나온다.
2. 평가기가 **원본 증거**를 읽기 전용으로 직접 조회할 수 있다(에이전트 보고서 경유 금지, ADR-0007).
3. 실험 전 기준선이 있다.
4. 마케팅 실험 하나의 영향으로 귀속할 수 있다(같은 기간에 다른 변경이 적다).

| 선택지 | 기준 충족 | 비고 |
|---|---|---|
| **A. 랜딩 페이지 1개의 주간 목표 행동 전환 수** (예: 문의·가입·다운로드) | 1~4 대체로 충족 | 분석 도구의 읽기 전용 API 필요. Phase A는 사람이 값을 입력하고 근거(화면·내보내기 파일)를 `evidence`로 첨부해도 된다 |
| B. 주간 리드 수 (CRM) | 2·3 충족, 1은 업종에 따라 부족 | 표본이 작으면 계속 `inconclusive` |
| C. 콘텐츠 반응(클릭·조회) | 1 충족, 4 약함 | 사업 성과와의 연결이 약하다 |
| D. 매출 | 4 약함, 1 부족 | 지연이 길고 귀속이 어렵다. Phase A에 부적합 |

**권장: A.** 실제로 어느 제품의 어느 페이지·행동인지는 `instance/`에 기록한다. 결정 전에 주간 사이클을 사람이 손으로 1~2회 돌려 보고(조사 → 실험 제안 → 측정) 관측 수가 나오는지 확인하는 것을 권한다. 이 수동 시험은 Phase A 전체의 사용자 가치를 미리 확인하는 가장 싼 방법이다.

## D3. 위험 변경 승인자 구성 (Q6)

ADR-0006은 위험 변경에 "2인 이상 또는 지정 역할" 승인을 요구하지만, 1인 운영에서는 불가능하다. Phase A에서 위험 변경은 정책 PR(런타임 API 없음)과 `require_approval` 판정을 받은 외부 부작용 업무 두 가지다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 2인 승인 (외부 조언자 등) | 원칙에 가장 충실 | 1인 운영에서 승인 대기로 업무가 멈춘다 |
| **B. 1인 승인 + 대기 시간 + 재인증** | 충동적·피싱성 승인을 막는다. 2인 체제로 바꾸기 쉽다 | 진짜 독립 검토는 아니다 |
| C. 1인 즉시 승인 | 빠르다 | 위험 변경과 일반 변경의 구분이 사라진다 |
| D. Phase A에서 위험 변경 미지원 | 단순하다 | 외부 게시 승인 테스트를 할 수 없다 |

**권장: B.** 정책 파라미터로 표현한다(값은 예시).

```yaml
risky_change:
  min_approvers: 1        # 2인 체제가 되면 2로 올린다 (이 변경 자체가 위험 변경)
  cooldown: 24h           # 승인 후 실행 가능까지 대기, 대기 중 취소 가능
  reauth_before_effect: true   # 실행 직전 사람 재인증 (D5)
  self_approval: false    # 요청자와 승인자가 같은 actor면 거부 (에이전트 요청은 항상 해당 없음)
```

다른 사람이 받아 쓸 때도 팀 규모에 맞게 값만 바꾸면 된다는 점이 B의 배포상 장점이다.

## D4. 시드 조직 (Q23)

**결정: A (오너 1 + `generalist` 1 + 읽기 전용 `registration-verifier` 1 + 초기 정책 v1, 기본 거부) (2026-10-19).** 기록: [ADR-0011](../adr/0011-adaptive-organization.md) Amendment (2026-10-19).

`task.policy_version_id`가 NOT NULL이고 업무는 `trial`/`active` 역할에만 배정되므로 A1에서 시드가 필요하다. ADR-0011은 실제 업무로 검증되지 않은 부서를 만들지 말라고 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 오너 + `generalist` + 읽기 전용 `registration-verifier`** | 등록 업무 템플릿과 바로 맞는다. 최소 권한 역할이 하나 생겨 정책 테스트가 쉽다 | 검증되지 않은 역할 1개를 미리 만든다 |
| B. 오너 + `generalist`만, 등록 업무는 `unassigned` | ADR-0011 원칙에 가장 충실. Phase B의 `unassigned` 신호를 미리 만든다 | Phase A에 사람이 수동 배정하는 경로를 따로 만들어야 한다 |
| C. 등록 업무를 고정 코어(시스템 업무)로 | 역할 문제가 사라진다 | 코어가 커지고, 등록이 "일반 업무의 첫 검증 사례"라는 의도(ADR-0010)와 어긋난다 |

**권장: A.** 시드 내용(형식만, 실제 이름은 `instance/`):

| 대상 | 시드 값 |
|---|---|
| `actor` | 오너 1명(`kind='human'`), 데몬·평가기·정책 엔진 시스템 주체 |
| `org_version` | v1, 부서 없음(또는 `core` 하나) |
| `role` | `generalist@v1`(주간 조사·실험 제안), `registration-verifier@v1`(읽기 전용) |
| `policy_version` | v1: 기본 거부, `internal` 읽기 허용, `write`는 업무 범위 내 허용, `external_effect`·`customer`/`public` 범위는 `require_approval` |

후속 정리: [task-spec 예시](../schema/task-spec.md)의 `planning`/`market-researcher`는 가상 예시로 두되, Phase A 시드와 맞추려면 `generalist`로 바꾼다.

## D5. 사람 승인 채널 인증 (Q25)

요건은 [trust-boundaries §3.1](../security/trust-boundaries.md): 에이전트 프로세스가 승인 경로에 도달할 수 없어야 한다. Q26(에이전트 격리 방식)과 함께 정해야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. Unix 도메인 소켓 + 피어 자격 증명(UID) 확인** | 승인 CLI만으로 시작할 수 있다. 에이전트를 다른 UID나 컨테이너로 돌리면 OS가 분리를 보장한다. macOS·Linux 공통 | Windows 미지원(WSL 필요). UID만으로는 같은 사용자 계정의 악성 프로세스를 막지 못한다 |
| B. 패스키(WebAuthn) | 사람 존재 확인이 강하다 | 내부 웹이 먼저 있어야 한다(Phase A 범위 밖) |
| C. OS 인증(생체 인증·관리자 암호) 매 승인 | 사람 존재 확인이 강하다 | 플랫폼마다 구현이 다르다 |
| D. TOTP | 구현이 쉽고 플랫폼 중립 | 비밀이 같은 기기에 있으면 의미가 약하다 |

**권장: A를 기본으로, 위험 변경에는 C(또는 D)로 재인증을 더한다. 내부 웹이 생기면 B로 옮긴다.** A의 약점(같은 계정의 다른 프로세스)은 에이전트를 별도 UID·컨테이너로 돌리는 Q26 결정으로 보완한다. Q26은 **컨테이너(Docker/Podman)** 를 우선 후보로 권한다. 파일·네트워크 격리를 한 번에 강제하고, 다른 사람이 같은 구성을 재현하기 쉽기 때문이다.

## D6. 라이선스

**결정: Apache-2.0 + DCO (2026-10-19).** 기록: 루트 `LICENSE`, README.

공개 저장소의 목적이 "다른 사람도 받아서 쓰게 하는 것"이라면 첫 공개 push 전에 정해야 한다. 라이선스가 없으면 법적으로는 아무도 사용·수정할 수 없다. (아래는 일반적 비교이며 법률 자문이 아니다.)

| 선택지 | 성격 | 맞는 경우 |
|---|---|---|
| MIT | 가장 관대, 특허 조항 없음 | 최대한 널리 쓰이게 하고 싶다 |
| **Apache-2.0** | 관대 + 명시적 특허 허여·상표 비허여 | 기업 사용자도 받아들이기 쉽게 하고 싶다 |
| AGPL-3.0 | 수정본을 네트워크 서비스로 제공하면 소스 공개 의무 | 다른 회사가 호스팅 서비스로 가져가는 것을 막고 싶다 |
| 소스 공개형(BSL 등) | 일정 기간 상업 사용 제한 | 자체 상용 호스팅을 계획한다 |

**권장: Apache-2.0 + DCO(커밋 서명으로 기여 권리 확인).** 자체 호스팅 서비스로 수익화할 계획이 있으면 AGPL-3.0을 고려한다. 어느 쪽이든 프로젝트 이름·로고는 라이선스와 별개로 상표로 남는다는 점을 README에 적는다.

사람이 확인할 것: 이 저장소로 수익을 낼 계획(호스팅, 지원 계약, 없음).

## D7. 확장 단위 계약

**결정: D (선언형 도메인 팩 + 게이트웨이 계약을 따르는 커넥터, 주간 사이클을 첫 팩 `packs/example-marketing`으로) (2026-10-19).** 기록: [ADR-0012](../adr/0012-extension-unit-contract.md).

여러 업종에 적용하려면 "업종별로 무엇을 더하는가"가 코어와 분리되어야 한다. 지금 계획은 주간 마케팅 사이클을 코어처럼 다룬다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 확장 단위 없음 (포크해서 수정) | 당장 할 일이 없다 | 업종마다 포크가 갈라져 코어 개선이 전달되지 않는다 |
| B. 선언형 팩만 (코드 없음) | 안전하다. 정책·검증 통제를 우회할 수 없다 | 업종별 결정론적 검증기·커넥터를 만들 수 없다 |
| C. 코드 플러그인 (패키지를 코어 프로세스에 로드) | 표현력이 가장 크다 | 플러그인이 DB·정책에 직접 접근할 수 있어 신뢰 경계가 무너진다 |
| **D. 선언형 팩 + 게이트웨이 계약을 따르는 커넥터** | 업무·루틴·검증 정의는 선언형으로, 코드가 필요한 커넥터·검증기는 별도 프로세스로 둔다 | 계약 설계가 필요하다 |

**권장: D.** Phase A에서는 계약의 **경계만** 정하고 범용 플러그인 체계는 만들지 않는다.

- **팩 구성:** `manifest`(이름, 버전, 요구 코어 버전, 필요한 도구), 업무 명세 템플릿(`workflows/`), 루틴(`routines/`), 검증 규칙(`evaluations/`, 결정론적 검사 id와 LLM 검증 프롬프트), 정책 **예시**(실제 정책은 `instance/`에서 사람이 승인), 측정 신호 정의(D2 형식).
- **커넥터·검증기 코드:** 도구 게이트웨이 계약으로만 호출되는 별도 프로세스. DB·`policies/` 접근 불가, 비밀값은 게이트웨이가 주입(trust-boundaries §3).
- **팩이 할 수 없는 것:** 정책 변경, 검증기·평가기 교체(버전 변경은 정책 변경 절차), 스키마 변경.
- **검증 방법:** 주간 시장 조사 사이클을 코어에 넣지 않고 첫 팩(`packs/example-marketing`)으로 구현한다. 코어 코드 수정 없이 두 번째 팩(예: 상품 등록 검증)을 더할 수 있으면 계약이 성립한 것으로 본다.
- **업종 중립성 보강(스키마):** `product`에 `kind`(`software|physical|service|other`)를 두고 `product_repo`는 선택으로 둔다(1:N이므로 0개 허용). 비용 원장은 LLM·도구 비용이 USD로 청구되므로 USD를 유지하되, 사업 성과 지표는 팩이 단위를 선언한다.

A0 영향: 저장소 골격에 `packs/`를 두고, 모듈 경계 lint에 "팩은 코어 내부 모듈을 참조하지 않는다"를 추가한다.
