# 스파이크 Q15: lease 파라미터

상태: 완료 (2026-10-19, 복구 지연 목표 120초는 2026-10-19 사람 확인) · 관련: [open-questions Q15](../open-questions.md), [phase-a §5 스파이크 4](../plans/phase-a.md), [recovery §2](../operations/recovery.md)

## 결론

**lease 90초, heartbeat 30초** (`DEFAULT_LEASE_PARAMS`, `packages/task-engine/src/params.ts`). 데몬 폴링 5초와 함께 쓰면 죽은 워커의 업무는 최대 약 95초 안에 인수된다. 이 값은 복구 지연 목표를 **120초**(2026-10-19 사람 확인)로 정해 고른 것이다. 목표가 바뀌면 아래 표에서 다시 고른다(목표 90초면 lease 60초·heartbeat 20초).

## 판정 방법 (시작 전에 고정)

phase-a §5의 기준을 그대로 썼다.

1. 정상 워커가 아래 지연 시나리오 S0~S3 모두에서 lease를 잃는 **오탐 인수가 0건**이다.
2. 죽은 워커의 업무가 **복구 지연 목표 안에** 인수된다. 최대 복구 지연 = lease + 폴링 주기(5초).
3. 1·2를 만족하는 조합 중 **heartbeat 쓰기 부하(run당 분당 heartbeat 수)가 가장 작은 것**.

지연 시나리오의 쓰기 대기 `w`는 1부 실측 최대값의 2배(측정 편차 여유)를 1초 단위로 올림한 값으로 정했다.

| 시나리오 | 내용 |
|---|---|
| S0 | 지연 없음 |
| S1 | 매 heartbeat가 쓰기 경합으로 `w` 늦게 기록된다 |
| S2 | S1 + 5분마다 heartbeat 1회가 `busy_timeout`(5초) 대기 끝에 실패해 한 주기를 건너뛴다 |
| S3 | S2 + 실패 직후 이벤트 루프가 10초 멈춘다(동기 작업·GC 등으로 heartbeat 타이머가 늦게 돈다) |

## 방법

스크립트: `node scripts/spikes/q15-lease.ts [--workers 8] [--seconds 10]`. 엔진의 실제 함수(`createTask`, `claimNextTask`, `heartbeat`, `findExpiredRuns`, `takeOverExpiredRun`, `submitRun`)를 그대로 부른다.

- **1부 실측.** 프로세스 N개가 같은 SQLite 파일(WAL, `busy_timeout` 5000ms)에서 쉬지 않고 heartbeat와 업무 생성 → lease 획득 → 제출을 번갈아 쓴다. heartbeat 한 번의 쓰기 트랜잭션 소요(대기 포함)와 `SQLITE_BUSY` 실패를 잰다. 실제 운영보다 훨씬 높은 쓰기율이다.
- **2부 모의.** 가짜 시계(`FakeClock`)로 30분을 진행한다. 정상 워커는 시나리오대로 heartbeat를 쓰고, 별도 인수자가 5초마다 만료 run을 찾아 인수한다. 인수가 일어나면 오탐이다. 복구 지연은 워커가 heartbeat 주기 안의 20개 시점에서 죽었을 때 인수까지 걸린 시간의 최대값이다.

## 결과

### 1부 실측 (macOS arm64, Node 24.22.0, SQLite 3.53.4)

| 프로세스 | heartbeat 수 | p50 | p99 | 최대 | `SQLITE_BUSY` 실패 | lease 상실 |
|---|---|---|---|---|---|---|
| 2 | 19,975 | 0.02ms | 0.11ms | 369ms | 0 | 0 |
| 8 | 19,200 | 0.02ms | 24ms | 2,688ms | 0 | 0 |
| 16 | 18,586 | 0.02ms | 96ms | 2,684ms | 0 | 0 |

최대 대기 약 2.7초 → `w` = 6초. `busy_timeout` 안에서 모두 성공해 실패는 없었다(S2·S3의 실패는 가정이다).

### 2부 모의 (폴링 5초, 30분)

| lease | heartbeat | S0 | S1 | S2 | S3 | S3 최소 여유 | 최대 복구 지연(모의) | heartbeat/분·run |
|---|---|---|---|---|---|---|---|---|
| 15s | 5s | 0 | 0 | 0 | 6 | -5s | 15s | 12 |
| 30s | 10s | 0 | 0 | 0 | 5 | -10s | 30s | 6 |
| 30s | 15s | 0 | 0 | 5 | 6 | -10s | 30s | 4 |
| 60s | 15s | 0 | 0 | 0 | 0 | 20s | 60s | 4 |
| 60s | 20s | 0 | 0 | 0 | 0 | 10s | 60s | 3 |
| 60s | 30s | 0 | 0 | 5 | 5 | -10s | 60s | 2 |
| **90s** | **30s** | 0 | 0 | 0 | 0 | 20s | 90s | **2** |
| 120s | 30s | 0 | 0 | 0 | 0 | 50s | 120s | 2 |
| 120s | 40s | 0 | 0 | 0 | 0 | 30s | 120s | 1.5 |

(S0~S3 열은 오탐 인수 횟수.) 모의의 복구 지연은 사망 시점과 폴링 시점이 맞물려 lease 값과 같게 나왔고, 이론상 최대는 lease + 폴링 주기다.

- 오탐 0건 조합: 60/15, 60/20, 90/30, 120/30, 120/40.
- 복구 지연 목표 120초(확정) 안: 60/15(65초), 60/20(65초), 90/30(95초). 120/30·120/40은 125초로 초과.
- 이 중 쓰기 부하 최소: **90/30**(분당 2회). S3 여유도 20초로 60/20(10초)보다 크다.
- 쓰기 부하 자체는 작다. 실측에서 8프로세스가 10초에 heartbeat·전이 약 4만 건을 썼으므로, 동시 실행 run 수십 개 × 분당 2회는 무시할 수준이다.

## 반영

- `DEFAULT_LEASE_PARAMS = { leaseMs: 90_000, heartbeatMs: 30_000 }`, 데몬 설정 예시에 `lease_ms`·`heartbeat_ms`·`poll_ms`(5000).
- `checkLeaseParams`가 heartbeat ≥ lease 조합을 거부한다.
- heartbeat 실패가 lease 상실이 아니면(예: `busy_timeout` 초과) 워커는 실행을 멈추지 않고 다음 주기에 다시 쓴다(S2 가정과 같은 동작).

## 열린 점

- **복구 지연 목표는 사람이 정한다**(phase-a §5). 2026-10-19 사람이 120초로 확인했다. 목표가 바뀌면 위 표에서 기준 3으로 다시 고른다.
- S3의 이벤트 루프 정지 10초는 가정이다. 어댑터·도구가 이벤트 루프를 10초 넘게 막으면 여유(20초)를 넘을 수 있으므로, 장시간 동기 작업은 A5 어댑터 계약에서 별도 프로세스·비동기로 두는 것을 권한다(recovery §2 "호출 중에도 heartbeat가 갱신되도록").
- 측정은 단일 macOS 호스트 한 대다. 느린 디스크(네트워크 파일시스템 등)에서는 1부를 다시 돌려 `w`를 확인한다(Phase A는 로컬 디스크 단일 호스트만 지원, recovery §2 규칙 5).
